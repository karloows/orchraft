# orchraft

orchraft automates the mundane, repetitive git/PR/issue chores of shipping software — branch naming, commit hygiene, review, landing, status — built first for solo developers with no one else to hand the busywork to. Windsurf has no plugin or slash-command mechanism to invoke orchraft's skills directly, so this file is context, not commands: when the user asks you to branch, commit, push, open/update a pull request, review one, merge one, or touch an issue or release, follow the rules below the same way you would if the matching skill had been invoked.

Non-negotiable: no commit, push, branch create/update, PR create/update/merge, PR comment/review, issue change, or release create/edit happens without the user's explicit go-ahead in the current turn. Approval never carries forward — a request to fix, address, or resolve something authorizes the edit only, never the commit/push that follows. The one exception is a scoped `Autonomous Mode` opt-in a repo owner writes, in either or both of two places: a `## Autonomous Mode` heading in their own `context/policies/approval-policy.md`, or the `autonomous` key in `.orchraft.json`/`.orchraft.jsonc` per `context/policies/config-policy.md` — the two are the same decision written in different places, not a lighter-weight path in the config file. Absent either, always ask first. Even with the override active, merging, force-pushing, deleting a branch or repository, and closing or reopening an issue stay gated regardless.

Read `context/policies/` in this repo before acting: `branch-policy.md`, `commit-policy.md`, and `writing-guidelines.md` define the exact format for a branch name, commit message, and PR text; `review-policy.md` defines severity levels and findings format for a review; `lore-policy.md` and `docs-policy.md` cover code comments and standalone docs respectively; `config-policy.md` documents `.orchraft.json`/`.orchraft.jsonc`, referenced above. Read the repo's own copy of each, not a memory of what it usually says.

What the lifecycle covers, in the rough order work moves through it: `warplan` plans an implementation before code is written; `quest` triages or files the GitHub issue; `ship` branches, commits, pushes, and opens/updates the pull request; `roast` reviews that PR against the repo's own policies; `land` merges it, syncs the base branch, and deletes the topic branch; `lore` fixes code comments/docstrings; `chronicle` drafts or updates standalone docs (README/ROADMAP sections, design docs); `yap` explains a diff, file, error, or policy with real citations; `runes` summarizes where a branch's work stands; `reckoning` lists declined review findings across the repo; `plunder` reports real shipping signal (PRs opened, findings fixed/declined, time-to-land); `muster` reports actionable open-PR state across every repo the account owns; `herald` drafts release notes from what actually merged; `warchief` chooses the next lifecycle step without granting itself approval; `watchtower` is a status nudge that would normally run ambiently on session start via a hook Windsurf has no equivalent for — ask for it directly instead. None of these are real commands here — they're names for the behavior above, grounded the same way: real diff, real history, no invented content.
